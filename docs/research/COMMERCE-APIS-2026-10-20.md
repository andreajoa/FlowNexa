# Commerce API implementation notes — 2026-10-20

Primary documentation research only. No merchant credentials, live store calls, deliveries, or app approvals were tested. Examples describe provider contracts, not verified production integrations.

## Shopify

**Authentication:** do not instruct new merchants to create legacy admin custom apps: these can no longer be created. Existing admin-created apps can still supply their installed access token. For new merchant-owned apps, exchange Dev Dashboard client ID and secret using `POST https://{shop}.myshopify.com/admin/oauth/access_token` with `grant_type=client_credentials`. Tokens last 86399 seconds; renew with the same grant before expiry. This grant only supports the app owner's own organization. A FlowNexa app serving unrelated merchants requires merchant authorization (authorization-code grant for a nonembedded app). Never expose credentials to the browser after saving. [Access tokens](https://shopify.dev/docs/apps/build/authentication-authorization/access-tokens), [organization restriction](https://shopify.dev/docs/apps/build/authentication-authorization/client-credentials-grant?lang=node), [legacy apps](https://shopify.dev/docs/apps/build/authentication-authorization/legacy/admin-custom-apps).

**Requests:** pin `POST /admin/api/2026-10/graphql.json`; `X-Shopify-Access-Token: TOKEN`, JSON request body. `read_products` and `read_orders` cover the principal catalog/order use cases. Inspect `currentAppInstallation { accessScopes { handle } }` rather than assuming scopes. Only the last 60 days of orders are normally available; older orders require approved `read_all_orders` in addition to order scope. Customer identifying information may be redacted until protected customer data requirements are satisfied; that review is separate from scope approval. [Scope reference](https://shopify.dev/docs/api/usage/access-scopes).

**Abandonment:** `abandonedCheckouts(first: 50, after: $cursor)` requires `read_orders` and the merchant's `manage_abandoned_checkouts` permission. This is checkout abandonment after contact information was supplied, not every anonymous cart. Fields include `id`, `createdAt`, `updatedAt`, `completedAt`, `abandonedCheckoutUrl`, and `customer`. Exclude recovered/completed records when preparing recovery. Poll with pagination and a stored cursor/checkpoint; recheck before dispatch. [Query](https://shopify.dev/docs/api/admin-graphql/latest/queries/abandonedCheckouts?example=retrieves-a-list-of-abandoned-checkouts).

**Webhooks:** use GraphQL `webhookSubscriptionCreate(topic: $topic, webhookSubscription: $input)` and inspect `userErrors`, not just HTTP 200. Current input supports destination `uri`. Useful topics include order creation/update/payment, fulfillment update, product creation/update and app uninstall. [Mutation](https://shopify.dev/docs/api/admin-graphql/latest/mutations/webhookSubscriptionCreate).

Verify the original request bytes using HMAC-SHA256 with the app client secret, encoded as Base64, against `X-Shopify-Hmac-Sha256`. Bind `X-Shopify-Shop-Domain` to the connection. `X-Shopify-Webhook-Id` identifies deliveries; `X-Shopify-Event-Id` identifies the merchant action shared across deliveries. Persist receipt before acknowledgment and handle replays/idempotency. [Webhook headers](https://shopify.dev/docs/api/webhooks/latest), [signing secret](https://shopify.dev/docs/apps/build/authentication-authorization/manage-credentials).

## WooCommerce and WordPress

**Woo authentication:** merchant generates Consumer Key/Secret in WooCommerce → Settings → Advanced → REST API. Use Basic Auth over HTTPS. Read-only keys suffice for reads; creating webhooks needs write permission. Alternatively `/wc-auth/v1/authorize` supports `app_name`, `scope=read_write`, `user_id`, `return_url`, `callback_url`; credentials arrive by a separate POST callback, so a return-page redirect alone is not proof of successful connection. Bind callbacks to a single-use server-side pending installation. [Authentication](https://developer.woocommerce.com/docs/apis/rest-api/authentication/).

Core endpoint family is `/wp-json/wc/v3`: orders, products, customers and webhooks. Create webhook with `POST /wp-json/wc/v3/webhooks`, JSON `{ "name": "FlowNexa orders", "topic": "order.updated", "delivery_url": "https://YOUR_HOST/HOOK", "secret": "RANDOM_SECRET", "status": "active" }`. `order.created`, `order.updated`, `product.created`, `product.updated` are useful event topics. [Webhook API](https://developer.woocommerce.com/docs/apis/rest-api/v2/webhooks/).

Verify `X-WC-Webhook-Signature` using Base64 HMAC-SHA256 of the original payload with the subscription's configured secret. Keep the webhook's ID and delivery ID for receipt tracking. [Delivery headers](https://developer.woocommerce.com/docs/apis/rest-api/v1/webhooks). Woo sends an initial ping when activating a webhook and disables a webhook after repeated delivery failures; expose connection health and reconciliation. [Operational behavior](https://woocommerce.com/document/webhooks/).

**Abandoned carts need an extension or companion plugin.** Core Store API `GET /wp-json/wc/store/v1/cart` exposes the current shopper/session cart, not a merchant-wide list of abandoned carts. Inference: polling this as an administrative abandoned-cart feed is incorrect; unpaid orders also cannot be relabeled abandoned carts. Implement server-side capture/recovery with explicit capability detection, or report the feature unavailable. [Store Cart API](https://developer.woocommerce.com/docs/apis/store-api/resources-endpoints/cart/).

**Tracking depends on installed extension.** Official Shipment Tracking uses `/wp-json/wc-shipment-tracking/v3/orders/{order_id}/shipment-trackings`. A separate Order Shipment Tracking product uses `/wp-json/wc/v3/orders/{order_id}/shipment-tracking`. Detect the namespace and normalize the result; do not promise tracking exists on vanilla WooCommerce or assume every extension stores the same metadata. [Shipment Tracking developer docs](https://woocommerce.com/documentation/products/extensions/shipment-tracking/shipment-tracking-developer-docs/), [Order Shipment Tracking API](https://woocommerce.com/document/order-shipment-tracking/).

**Plain WordPress is a separate content connection.** Use username plus revocable Application Password over HTTPS, test `/wp-json/wp/v2/users/me`, then read posts/pages as permitted. Application Passwords inherit that user's capabilities. WordPress core REST resources do not supply a universal commerce order/cart model: WooCommerce or another explicit ecommerce adapter is required. [Application Passwords](https://developer.wordpress.org/advanced-administration/security/application-passwords/), [core resources](https://developer.wordpress.org/rest-api/reference/).

## Nuvemshop / Tiendanube

Use a registered partner app and OAuth merchant consent. Authorize at `https://www.nuvemshop.com.br/apps/{app_id}/authorize?state=...`; exchange code at `POST https://www.nuvemshop.com.br/apps/authorize/token`, JSON `client_id`, `client_secret`, `grant_type=authorization_code`, `code`. Response `user_id` is the store ID. Bind single-use state to the logged-in workspace. Scopes are configured on the partner app, not dynamically by authorization URL; scope changes require reinstall/new token. Request `read_orders`, `read_products`, and `read_customers` only if full customer objects are needed; fulfillment resources have `read_fulfillment_orders`. A manual token is an already authorized app token, not a generic merchant password. [Authentication and scopes](https://tiendanube.github.io/api-documentation/authentication).

Current docs use `https://api.nuvemshop.com.br/2025-03/{store_id}` (or `api.tiendanube.com`) and `Authorization: Bearer TOKEN`, plus a descriptive `User-Agent: FlowNexa (SUPPORT_EMAIL)`. Older `v1` examples differ; pin the version and verify headers against the actual store before launch. [Current getting started](https://nuvemshop.dev/en-US/api/getting-started).

Read `/products`, `/orders`, `/orders/{id}`, `/checkouts`. Orders expose `shipping_tracking_number` and `shipping_tracking_url`, potentially null. The nested customer requires `read_customers`; respect nulls and do not invent tracking. New multi-inventory order APIs are recommended by the provider; normalize fulfillment records where available. [Order schema](https://tiendanube.github.io/api-documentation/v1/resources/order).

Abandoned `/checkouts` requires `read_orders`; a checkout is only recorded after the shopper reaches the second checkout step. Creation can lag up to six hours. Fetchable for 30 days, deleted after 90 days. Do not label this real-time anonymous cart monitoring. [Abandoned checkout API](https://tiendanube.github.io/api-documentation/v1/resources/abandoned-checkout).

`POST /webhooks` accepts `{ "event": "order/paid", "url": "https://YOUR_HOST/HOOK" }`. Other useful events: `order/created`, `order/updated`, `order/fulfilled`, `product/created`, `product/updated`, `app/uninstalled`. Notifications contain `store_id`, `event`, resource `id`: fetch the resource before normalization. Verify original bytes against **hex** HMAC-SHA256 in `x-linkedstore-hmac-sha256` using app secret (not the API token). Acknowledge within three seconds after durable persistence. The docs do not guarantee ordering and warn against deduplicating solely by identical bodies; use resource-version idempotency for downstream effects. Implement mandatory data-request/redaction callbacks before public app launch. [Webhook contract](https://tiendanube.github.io/api-documentation/v1/resources/webhook).

## Automation contract and remaining verification

Engineering recommendations: expose provider capability status; encrypt secrets server-side; redact logs; bind every resource lookup and webhook to workspace plus connection; validate merchant URLs against private-network/redirect SSRF; bound timeouts and response sizes; use pagination, retry/backoff, durable receipts and resource checkpoints. Read-only order lookup must verify the requesting customer's ownership before returning tracking or purchase data. Store currencies remain the original ISO currency, independently of FlowNexa subscription-pricing locale.

A store API connection does not itself authorize promotional DMs or establish a verified association between a store email and an Instagram recipient. Prepare catalog events and campaign drafts, then use the channel's independently authorized sender and eligibility/consent checks. Do not broadcast a new product automatically to every stored buyer. Meta's current official messaging pages returned HTTP 429 during this research, so exact channel rules were **not reverified** here: [official Instagram messaging overview](https://developers.facebook.com/documentation/business-messaging/instagram-messaging/overview). Provider app installation, OAuth callback, permissions, test order/cart/tracking and webhook retry must still be exercised with real authorized test stores before claiming end-to-end production readiness.

## Provider code review against current schema

Reviewed `src/commerce/providers.js` on 2026-10-20; findings describe the snapshot before subsequent corrections.

- **Shopify abandoned checkout query is invalid:** `AbandonedCheckout` has no direct `email` field. Select `customer { email }` and compare that nullable field. [Object fields](https://shopify.dev/docs/api/admin-graphql/latest/objects/AbandonedCheckout).
- **Shopify abandoned-checkout `email:` search is undocumented:** supported filters include `created_at`, `email_state`, `id`, `recovery_state`, `status`, `updated_at`, and default search. Use `recovery_state:not_recovered`, paginate through `after` and `pageInfo { hasNextPage endCursor }`, and perform exact customer email checks. Bound scans must report incomplete results rather than imply no cart exists. [Query arguments](https://shopify.dev/docs/api/admin-graphql/latest/queries/abandonedCheckouts).
- **Shopify topics are spelled correctly:** `ORDERS_CREATE`, `ORDERS_UPDATED`, `FULFILLMENTS_CREATE`, `PRODUCTS_CREATE`, `APP_UNINSTALLED` are valid. Consider `FULFILLMENTS_UPDATE` to capture tracking attached after initial fulfillment. Capabilities should recognize write scopes that imply read permissions instead of only checking literal `read_*`. [Topic enum](https://shopify.dev/docs/api/admin-graphql/latest/enums/WebhookSubscriptionTopic), [scope semantics](https://shopify.dev/docs/apps/build/authentication-authorization/manage-access-scopes).
- **Nuvemshop version upgrade must include tracking mapping:** `shipping_tracking_number` and `shipping_tracking_url` describe the legacy v1 order, not the current 2025-03 order schema. Request `GET /orders?q=NUMBER&aggregates=fulfillment_orders&page=1&per_page=50` and normalize `fulfillments[].tracking_info.code` / `.url`. `q` validly searches number, customer name, or email, so exact number/email comparison remains necessary; a five-result cap can miss a legitimate match. [2025-03 orders](https://nuvemshop.dev/en-US/api/resources/2025-03/order).
- **Nuvemshop checkout filtering exists in 2025-03:** use `/checkouts?contact_email=ENCODED_EMAIL&per_page=50&page=1`; continue pages or return an explicit cursor/truncated result. Current code reads the first 50 storewide and may miss the shopper. `contact_email`, `completed_at`, `abandoned_checkout_url` are valid response fields. [2025-03 checkouts](https://nuvemshop.dev/en-US/api/resources/2025-03/abandoned-checkout).
- **Nuvemshop product mapping is valid:** localized `name`, `canonical_url`, variants' `price`, `published=true`, and `q` are documented. Add `sort_by=created-at-descending` for newest-first behavior. Pagination uses `page` and `per_page` (maximum 200 for products). [2025-03 products](https://nuvemshop.dev/en-US/api/resources/2025-03/product).
- **Nuvemshop topics confirmed:** `order/updated` and `app/uninstalled` are valid, as are `order/created` and `product/created`; no correction to those strings is needed. The earlier legacy transport (`/v1`, `Authentication: bearer`) should not be silently combined with newer fields: pin and test one contract. [Webhook events](https://tiendanube.github.io/api-documentation/v1/resources/webhook), [current transport](https://nuvemshop.dev/en-US/api/getting-started).

These are documentation/schema checks, not authenticated provider validation.
